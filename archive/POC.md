# POC — 家庭AI研究プロジェクト（家事時短・献立）
更新日: 2026-09-24 / 作成: Claude Code
Source: 03（17〜19章、34〜37章）＋ Owner指示（2026-09-24、DEC-007）

**PoC-Aの最小実装範囲は確定・実装済み**（`app.html`）。以下は03全体のフルループと、実際に採用したPoC-Aの範囲の両方を記録している。

## 0. PoC-A（確定・実装済み）

> 使いたい食材を自由入力 → モード選択（最速/普通/料理したい） → 献立3候補 → 1つ選ぶ → 食後評価（👍😐👎＋また作りたい？）

冷蔵庫写真・レシート・Inventory Candidate生成は**意図的に含めない**（DEC-007）。理由は「在庫認識精度」ではなく「献立を考える負担を減らせるか」を先に検証したいため。

- 実装：`app.html`（Vanilla JS + localStorage、レシピDB42件を食材一致度でスコアリング）
- 検証：Playwrightで動作確認済み（コンソールエラー0件）。「鶏むね肉・キャベツ・卵」入力→「鶏むねとキャベツの塩炒め」等が候補に出ることを確認
- 計測：献立を決めるまでの秒数を自動計測し記録（成功指標1「献立決定時間」に対応）
- 次にやること：実際の夕飯で数日使ってみて、5つの成功条件（下記1章）を見る

## 1. PoC候補ループ（03 17章）

```text
冷蔵庫写真 / レシート
        ↓
AIが在庫Candidate生成
        ↓
今日のモード選択（時短 / 楽しむ）
        ↓
AIが献立提案（候補数は未確定。HYPOTHESES.md HYP-002参照）
        ↓
料理
        ↓
完成写真
        ↓
家族評価（👍/😐/👎）
        ↓
在庫推定更新
        ↓
家族嗜好更新
        ↓
次回推薦
```

このループの前半（在庫Candidate生成）を省略し、「使いたい食材の自由入力＋モード選択→献立提案」だけに絞った、さらに簡易なPoCから始める案もある（03 34章 Phase 1）。どこまで削るかは次ステップで決める。

## 2. PoC UIイメージ（03 18章）

**STEP 1**：今日どうする？ → ⚡最速 / 🍳普通 / 🎨料理したい

**STEP 2**：AI「今日はこちらがおすすめです」→ 料理名・所要時間・買い物要否・洗い物量

**STEP 3**：料理後「今日どうでした？」→ 👍 / 😐 / 👎

## 3. 必ず入れるもの：Learning Loop（03 19章）

単なる「冷蔵庫写真→レシピ」で終わらせない。少なくとも以下を次回推薦に使う：
- 家族評価
- 過去の採用/却下
- 実際に作ったか

## 5. PoCで最低限検証したい問い（03 35章、詳細はHYPOTHESES.md）

- Q1：冷蔵庫写真だけで実用的な在庫Candidateを作れるか
- Q2：3候補より1候補の方が楽か
- Q3：👍/😐/👎だけでも家族嗜好を学習できるか
- Q4：Household Loadはユーザーに価値があるか
- Q5：Evidenceベースの自動推定で手入力を十分減らせるか

## 6. 成功指標（03 36章）

PoCでは**アプリ利用時間を増やすことを成功にしない**。むしろアプリを触る時間が短い方が成功である可能性がある。

候補指標：献立決定時間／手入力時間／買い物時間／調理時間／洗い物時間／食品廃棄／献立を考えた回数／家族満足度／提案採用率

（01 11章の「家事」評価指標表には、上記に加えて具体的な仮目標値の案がある：認識精度＝食品候補の適合率90%以上・再現率80%以上、訂正の負担＝レシート1枚あたり中央値60秒以下、献立の採用＝提示日のうち50%以上を実際に作る、など。これらは01独自の仮置き数値であり、03では明言されていない。次ステップでPoC最小仕様を確定する際、採用するかどうか検討する）

## 7. このプロジェクトで避けたいもの（03 37章、NG集）

1. 機能を増やすことが目的になる
2. AIのために人間がデータ入力する
3. 完璧な在庫DBを作ろうとする
4. すべて自動確定する
5. レシピ生成精度だけを競う
6. 健康・栄養・節約などを全部初期PoCに入れる
